# Object detection, obstacle avoidance, and trajectory changes

This document describes the algorithms **currently implemented** for the simulated Tello mission. The relevant code is in [`scripts/depth_navigation.py`](scripts/depth_navigation.py), [`scripts/drone_zigzag.py`](scripts/drone_zigzag.py), and the mission planners in [`scripts/coverage_plan.py`](scripts/coverage_plan.py) and [`scripts/roi_plan.py`](scripts/roi_plan.py).

The mission CLI now defaults to YOLO with known-size metric geometry in an
RGB-only controlled world; see the [YOLO guide](docs/yolo-rgb-navigation.md).
The synthetic RGB-D path described below is the `--depth-source gazebo` baseline.
The [dense RGB experiment guide](docs/rgb-depth-experiment.md) explains the failed
Depth Anything experiment. A controlled RGB-only YOLO pillar flight has passed;
physical autonomous avoidance and camera localization remain unvalidated.

## Current RGB-only mission

The default `--coverage-mode adaptive` tracks ground observed in synchronized
downward RGB views. It selects useful sweep segments, can finish a bypass on a
later lane, and returns for remaining visible patches. It does not enforce the
nominal overlap on each flown pass. A* connections and checked rounded corners
respect the inflated obstacle map; adaptive sweep connections remain inside the
ROI. Coverage excludes the estimated obstacle envelope separately and does not
count it as observed ground.

The launcher also spawns a small blue box at a random point inside the ROI.
It is currently a scene target only; identification, visual position estimation
and Go2 handoff are future work. The remaining sections describe the legacy
synthetic-depth pipeline and its fixed-lane behavior. For the current RGB
implementation and measured results, use the [YOLO guide](docs/yolo-rgb-navigation.md).

## How objects are detected in the Gazebo-depth baseline

The drone uses the simulated front **RGB-D depth camera**. Detection is geometric: it finds measured surfaces that could obstruct the drone. It does **not** use YOLO, a neural network, RGB object classification, or known obstacle models. The camera's depth channel is generated by Gazebo; the physical Tello is not being tested here.

1. The navigator receives a depth image, camera intrinsics, and the drone's own time-synchronized pose. It samples the depth image every four pixels and keeps finite distances between 0.08 m and 8 m.
2. It back-projects each valid pixel into a 3D point, then uses the camera mounting angle and drone pose to express that point in world coordinates.
3. It removes points at or below 0.20 m (mainly the ground) and above 10 m. Points are stored as **15 cm surface voxels**; a voxel needs at least two points in an integration to be added. The map starts empty and grows as the camera sees new surfaces.
4. For horizontal collision planning, it selects observed surface voxels within approximately 0.30 m of the cruise altitude, allowing for voxel size. The resulting XY points represent measured obstacles at flight height.

Only visible surfaces enter the map. The detector does not infer an object's complete shape or identify its class. It uses the simulator pose of **the drone only**, never the simulator's obstacle names, poses, or geometry. [`scripts/obstacle_map.py`](scripts/obstacle_map.py) reads simulator geometry for reference and tests, but is not used by the mission's detector or avoidance path.

## How obstacles are avoided

The avoidance algorithm is **A\* search on a two-dimensional occupancy grid** at the chosen flight altitude. Grid cells are 20 cm wide. Observed obstacle points block nearby cells with a nominal 50 cm clearance, plus a grid discretization allowance. Planning stays within the mission's XY extent plus a 2 m margin.

For each planned waypoint leg, the navigator first checks whether the current route is clear of blocked cells. An unobstructed leg starts with a straight route. If the route is blocked, A\* searches eight neighboring cells, disallows diagonal corner cutting, and finds a route around the observed obstacle. Its cost includes travel distance, a preference for the previous safe detour, and a penalty for cells already visited. A line-of-sight check then removes unnecessary intermediate turns without crossing blocked cells.

Unknown space is only a candidate route; it is **not certified clear**. Before moving, the drone turns toward the next segment and waits for a fresh depth frame synchronized with its pose. A new observation updates the map. If it blocks the remaining route, the navigator runs A\* again; otherwise it keeps the current detour. It checks each short movement against the inflated grid before issuing it.

## How the drone changes trajectory

The mission planner first creates the intended coverage waypoints. For the rectangle this is a serpentine zigzag, choosing the feasible end closest to the user-defined home position; other region shapes use their corresponding planned legs. Avoidance operates **locally on each leg** and does not move the home position.

When an obstacle blocks a leg, the navigator computes a detour from the drone's current position to a clear point farther along that same leg. It follows the detour, rejoins the original leg after the obstruction, and continues the remaining waypoints. If new measurements block the detour, it replans from the current position. This can happen several times while the object comes into view.

The drone executes each segment as a sequence of movements of **at most 18 cm**. It rotates to face the intended movement, observes the scene, checks the next step, and advances. In this simulation, [`move()`](scripts/drone_zigzag.py) interpolates position and yaw with a smoothstep curve and sends Gazebo `set_pose` requests at about 20 steps per second. This is **kinematic pose control**, not a physical flight controller or a dynamics-based collision response. The live panel displays the measured flight trail, observed surface voxels, and current local route.

If depth or pose data are stale or invalid, or if the safety margin is already occupied, the navigator stops translation and reports an error. An inaccessible intermediate waypoint is marked skipped; if the return-home point is inaccessible, the mission does not automatically descend. The map retains old surface voxels, so moving obstacles are not yet handled reliably. A detour can leave parts of the originally intended coverage unflown.
